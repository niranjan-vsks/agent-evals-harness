# P8: Home dashboard (1 read-only summary endpoint, 1 view)

## §0 CLAIM THIS COLD

Read: `STATE.md` sections 0, P7, "Audit fixes (code)"; this card; `web/src/styles/tokens.css`,
`web/src/components/AppShell.vue`, `web/src/views/CompareView.vue` (reuse its cards, chips,
Interval and chart style); `api/src/compare/`, `api/src/export/` (how the API reads trials).

Scope: 1 new endpoint `GET /summary` and 1 new view at `/` (the current `/` redirect to
Configs moves to `/configs`; nav gains "Overview" first). Read-only. No new tables, no
change to statistics, no change to any existing view beyond the nav entry. The dashboard
shows numbers the API already stores; it computes nothing a comparison has not already
computed (it reads persisted `comparison_run` rows for verdicts).

Out of scope: time-range filters, auto-refresh beyond the existing 3 s poll, any new chart
library, any metric not listed in §4.

## §1 WHAT IS ALREADY TRUE

- Tokens, app shell, DataTable, Skeleton, EmptyState, Interval (with CI bar), count-up
  numbers and the 3 SVG charts exist from P7; dark default, light toggle.
- `comparison_run.result` holds the full payload of every persisted comparison, including
  `aggregate.verdict`, `ci_low`, `ci_high`, `cost`, `latency_ms`, `tokens`.
- `trial` rows carry `cost_usd`, `latency_ms`, tokens, `status`, `passed`, `failure_category`.
- The demo stack with real data is on `http://localhost:8280` (STATE.md P5).

## §2 WHAT THIS IS

The first screen a reviewer sees: the state of the whole evaluation effort on 1 page,
in 5 seconds. Numbers first, then the latest verdict, then where the money went.

## §3 THE DESIGN IDEA

The dashboard is a view over existing rows and persisted comparisons; it never
recomputes a statistic. A verdict appears on the dashboard only if a `comparison_run`
row exists for it, so the dashboard can never disagree with a Compare screen.

## §4 DATA

`GET /summary` returns:

```jsonc
{"totals":{"experiments":int,"configs":int,"tasks_current":int,"trials_done":int,
           "trials_errored":int,"spend_usd":number,"models":int,"harnesses":int},
 "latest_comparisons":[{"comparison_run_id","experiment_id","experiment_name","axis",
   "config_a_name","config_b_name","verdict","delta","ci_low","ci_high","reliability",
   "judge_policy_applied","computed_at"}],            // newest 5, from comparison_run
 "configs":[{"config_id","name","harness_id","model_id","memory_mode","trials_done",
   "pass_rate","mean_cost_usd","mean_latency_ms","mean_input_tokens","mean_output_tokens"}],
                                                      // over done trials, per config
 "failures":{"<category>":int},                       // over done and failed trials
 "recent_experiments":[{"id","name","status","n_trials","progress":{done,errored,pending,running},"created_at"}]  // newest 8
}
```
Pure aggregation in `api/src/summary/summary.service.ts` (tested with seeded rows);
`pass_rate` is mean of per-task pass rates (macro, as DESIGN 9.1), not raw trial mean.
Spend is the sum of `trial.cost_usd` over done trials.

## §5 THE HARD PART

A dashboard that quietly contradicts the Compare page. Guard: verdicts come only from
`comparison_run`; the config pass rate uses the same macro average as `compare.ts`
(import or copy the 1 function, with a test asserting equality on a fixture); every
number has its unit next to it (USD, ms, tokens).

## §9 STOP CONDITIONS

- Any number on the Overview cannot be sourced from an existing row or persisted
  comparison without new statistics. Stop and report; do not compute it in the UI.
- The equality test between the dashboard pass rate and `compare.ts` cannot be made to pass.
