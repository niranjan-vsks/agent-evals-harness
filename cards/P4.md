  Replace the placeholder with the Vite build; nginx proxies `/api/*` to `api:3000`.

## §2 WHAT THIS IS

The screens the video walks through: define a config, run an experiment, compare with
confidence, drill into a failed trial and see why from the trace alone.

## §3 THE DESIGN IDEA

The UI never computes a statistic or a verdict; it renders the API's payload, including
its caveats, verbatim. Every number that has an interval is shown with it; every
comparison shows its reliability and judge policy badges above the numbers, not in a
footnote.

## §4 DATA

No schema changes. Client types in `web/src/api/types.ts` mirror the API DTOs; generate
them by hand from the controllers (there is no OpenAPI step in scope; §10.1).

## §5 THE HARD PART

A trial inspector that lets a reader answer "why did it fail" without opening the DB.
That means: the task prompt, the final response, the extracted answer vs expected (from
`grader_results[].details`), the judge reasoning verbatim, the event timeline with tool
args and results expanded on click, memory reads and writes highlighted, the system
prompt available (collapsed), and the exit reason and step count at the top.

## §8 GATES

1. Harness: `npm test` (Vitest) N of N; the verdict rendering test is mandatory.
   Mutation test: flip the noise condition in the component to `ci_low < 0 && ci_high > 0`
   (strict) and show the boundary fixture (`ci_low = 0`) makes the test red; restore.
2. Audit: `docker compose exec web` is nginx and has no test runner; run the Vitest suite
   in the build stage of the Dockerfile so `docker compose build` fails on red.
3. Typecheck and build: `vue-tsc --noEmit` clean; `vite build` clean.
4. The walk, in a browser against `docker compose up`: (a) create a config and see a
   validation error for `minimal_loop` with skills on, then create it valid; (b) create an
   experiment with the 2 Hermes memory configs, 4 tasks, N=1, type a hypothesis, start,
   watch counts move; (c) open Compare and read the verdict sentence and the interval;
   (d) open a failed trial and point to the line that explains it (grader detail or a
   tool result); (e) export CSV downloads. Record the experiment id and a screenshot path
   in STATE.md.
5. Live: compose stack, gate 4.

Append a STATE.md section before this phase is done.

## §9 STOP CONDITIONS

- A view needs data the API does not return and cannot be composed from 2 calls. Report
  the field; do not add computation to the UI.
- The trace for a real trial exceeds what the browser renders smoothly (more than about
  2,000 events). Default is to virtualize the list; if that is not enough, report.
- The same assertion fails 3 times under 3 different fixes.

## §10 OPEN QUESTIONS

1. Hand-written types vs OpenAPI generation. Default: hand-written; NestJS Swagger is not
   in scope.
2. Polling vs SSE for progress. Default: poll `GET /experiments/:id` every 3 s while
   status is `running`.
3. Where the trial list for a config pair lives. Default: the experiment detail page with
   a config filter; no separate page.
4. Dark mode, responsive layout. Default: no; a single desktop layout with system fonts.
