## §1 WHAT IS ALREADY TRUE

- The 2 configs for the axis are defined in DESIGN.md 10.1; the candidate model and the
  judge model are named in STATE.md P1 (§10.4 of that card). Create the configs through
  the API; their hashes go into 10.4.
- `POST /experiments` requires a hypothesis in `draft`; after `start` it is immutable
  (D-10). The hypothesis text is DESIGN.md 10.1 H1 to H3 verbatim.
- `GET /experiments/:id/pilot` returns variances and projected widths and no delta (P3
  scenario j). The N rule is DESIGN.md 9.7: smallest N in {3, 5, 8} with `h(N) ≤ 0.15`.
- `POST /experiments/:id/extend` appends trials (D-9); pilot trials are reused.
- `npm run judge:sample -- --n 30` writes a blind file; `npm run judge:kappa` reads
  `experiments/judge-validation/labels.jsonl` and writes a `judge_validation` row whose
  policy the compare endpoint applies (D-16, DESIGN 8.3).
- `MAX_CONCURRENT_TRIALS` default 2; `rate_limit_events` is recorded per trial.
- Cost per trial is computed from `price_snapshot` (D-7); `harness_cost_usd` is Hermes's
  own estimate and is reported next to it, not instead of it.

## §2 WHAT THIS IS

The evidence. 1 single-axis experiment, pre-registered, run under the method, with the
judge checked and the limits stated, plus the documents a reviewer reads first.

## §3 THE DESIGN IDEA

Commit to the prediction before the data (hypothesis in the draft, N from the pilot's
variance only), run, then report against the prediction including the parts that came
out "noise". The write-up is 3 trajectories and a table, not a narrative.

## §7 SLICES

S1. Create the 2 configs and the draft experiment (hypothesis pasted, axis label,
    phase pilot, N=3, seed recorded). Start. Record start time and `MAX_CONCURRENT_TRIALS`.
S2. When the pilot is `completed` or `partial`: call `/pilot`, write the variance and
    projected widths and the chosen N into STATE.md, then `/extend` to N. Do not call
    compare before this is written.
S3. When the full run finishes: `judge:sample -- --n 30`; label; commit labels;
    `judge:kappa`; record kappa, CI and policy.
S4. Compare with `?persist=1`; export JSON (with traces) and compare.csv; commit under
    `experiments/results/`. Fill DESIGN.md 10.4: pilot numbers, N, aggregate and
    by_category with CIs and verdicts, sign test, per-task table (22 rows), cost/latency/
    tokens table, kappa, 3 trajectories (trial ids with the exact event or grader detail
    that explains the outcome), conclusion against H1 to H3, actual spend.
S5. README.md and VIDEO.md. If budget remains, run the secondary experiment (DESIGN 10.3)
    at the same N and add a short 10.5.

## §9 STOP CONDITIONS

- The pilot shows every memory-dependent task at the same pass rate under both configs
  (no variance to work with). Report the per-task table; the architect decides whether to
  switch axis (the architect's note: "tell me and we switch").
- More than 10 percent of trials end `errored` after retries. Pause (the breaker may have
  done it), report the error classes, do not extend.
- Kappa below 0.4. Do not re-label; report, apply the `excluded` policy, and write 10.4
  on deterministic tasks only with the judge tasks in a separate table.
- Actual spend exceeds 25 USD before the full run completes. Stop and report the export.
